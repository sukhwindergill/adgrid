# REST Campaign API — Design

Competitive Parity Program, Phase 6, G21 (REST API half — the CSV bulk screen import half already shipped, see `docs/superpowers/specs/2026-09-08-csv-bulk-screen-import-design.md`):

> REST campaign API with scoped keys.

## Problem

Every campaign action on AdGrid today requires the dashboard UI: `CreateCampaign.jsx`'s wizard, `AdvDashboard.jsx` for status, `BillingView.jsx` for payment. An advertiser running campaigns programmatically — a media-buying tool, an internal ops script, an agency managing many advertiser accounts at once — has no way in. This is the same class of gap CSV bulk import closed for operators (many screens, one action) but for advertisers managing campaigns at scale.

## Goals

- An advertiser can list, read, create, update (pre-payment), and cancel their own campaigns via a REST API, scoped to their own account only.
- API keys are scoped per-advertiser (never a platform-wide key), generated/revoked from the dashboard, shown once, stored hashed — same precedent as the conversion-postback key (G9) and `screen_token`.
- A campaign created via the API and submitted for payment is charged the same way the dashboard already charges one: `charge-campaign`'s existing off-session Stripe flow against the advertiser's saved default payment method. No new payment infrastructure, and the API never touches raw card data.

## Non-goals

- **No new payment method entry via the API.** An advertiser must have already saved a default payment method through the dashboard (`BillingView.jsx`) before an API-submitted campaign can be charged; the API can trigger a charge against what's already on file, not collect a card. This keeps PCI scope exactly where it already is (Stripe Elements in the dashboard) and doesn't reopen it for a server-to-server flow.
- **No screen-search/discovery endpoints in v1.** Creating a campaign via the API requires the caller to already know which `screen_id`s they want (e.g. from a prior CSV export, or hardcoded IDs an agency manages repeatedly) — no `/screens?radius=...` search endpoint. `MarketplaceView.jsx`'s targeting/radius search stays a dashboard-only feature for now; exposing it is a plausible v2 once there's real API demand for it.
- **No webhook/event-push API.** Status changes (approved, live, delivery data) are pull-only in v1 (`GET /campaigns/:id`) — no outbound webhook registration. The existing in-app notification system stays the only push mechanism. A webhook API is a natural v2 once there's a specific integration asking for one.
- **No write access to delivery/reporting data.** Scans, impressions, conversions stay read-only via the API (a `GET /campaigns/:id/delivery` summary endpoint) — this API is for campaign lifecycle management, not a general data-export replacement for the dashboard's existing CSV exports.
- **No team/multi-user key scoping beyond the account.** A key is scoped to one advertiser account exactly the way the dashboard session is — it does not carry the delegated-access nuance `account_grants`/`AccessSettingsView.jsx` already has for human users. A delegated team member with dashboard access does not automatically get API access; API keys are generated by the account owner only. Extending API scoping to match delegated roles is a plausible v2, not required to ship a useful v1.

## Data model changes

### New table: `api_keys`

```sql
create table api_keys (
  id uuid primary key default gen_random_uuid(),
  advertiser_id uuid not null references profiles(id) on delete cascade,
  name text not null,                 -- advertiser's own label, e.g. "Media buying tool"
  key_prefix text not null,           -- first 8 chars of the plaintext key, shown in the dashboard list so an advertiser can tell keys apart without re-seeing the full value
  key_hash text not null,             -- SHA-256 of the full key, same hashed-at-rest precedent as postback_key
  scopes text[] not null default '{campaigns:read,campaigns:write}', -- fixed to this one pair in v1 (see below); the column exists now so v2 scope granularity doesn't need a schema migration
  last_used_at timestamptz,
  revoked_at timestamptz,
  created_at timestamptz not null default now()
);
```

RLS: advertiser manages their own keys' metadata (`FOR ALL USING (advertiser_id = auth.uid())`) for listing/naming/revoking — but `key_hash` is never selected back to the client after creation (the generating edge function returns the plaintext key once in its response body, not written anywhere the client can re-read; the stored row's `key_hash` column is covered by a `SELECT` policy that still returns it in a raw `select *`, so the *dashboard UI* is the actual boundary here — it never renders `key_hash`, only `key_prefix`/`name`/`last_used_at`/`revoked_at`. This mirrors how `screen_token` and the G9 postback key hash are already technically readable via a broad table `SELECT` but never surfaced by the UI that reads them — flagged here rather than silently repeating the pattern a third time without naming it).

`scopes` is fixed to `{campaigns:read, campaigns:write}` in v1 (every key gets both — there is no read-only key option yet) — the column exists so a v2 "read-only key" or finer-grained scope doesn't need a schema change, not because v1 actually varies it.

No changes to `bookings` or any other existing table — an API-created campaign is an ordinary `bookings` row, created through the same insert shape `CreateCampaign.jsx` already uses (see Architecture).

## Architecture

### 1. Key generation (dashboard-side)

New "API Keys" section in `AdvIntegrationsView.jsx`, alongside the "Conversion Tracking" tab shipped for G9 — same visual pattern (generate → show once → copy → done), same client-side generate-and-hash approach (`generatePostbackKey`/`hashPostbackKey`-shaped functions, new `src/lib/apiKey.js` mirroring `src/lib/postbackKey.js` exactly, prefixed `agak_` instead of `agpk_` to keep the two key families visually distinguishable in the UI and in support conversations). The advertiser names the key, generation inserts the row (`key_prefix` = first 8 chars, `key_hash` computed client-side same as the postback key), and the full key is shown once with a copy button. Existing keys list shows name/prefix/created/last-used/revoked state with a "Revoke" action (`revoked_at = now()`).

### 2. Auth middleware (shared across all API endpoints)

New `supabase/functions/_shared/apiKeyAuth.ts`:

```ts
export async function authenticateApiKey(
  supabase: SupabaseClient,
  req: Request,
): Promise<{ advertiserId: string } | Response> {
  // Authorization: Bearer agak_... -- hash it, look up api_keys by key_hash,
  // reject if not found or revoked_at is set, update last_used_at
  // (fire-and-forget, doesn't block the response), return { advertiserId }.
  // On any failure, returns a ready-to-send 401 Response so every endpoint
  // does `const auth = await authenticateApiKey(...); if (auth instanceof Response) return auth;`
  // rather than duplicating the error-shape decision at each endpoint.
}
```

Every endpoint below rate-limits by the presented key (`rateLimited(supabase, `api:${keyPrefix}`, ...)`, same `_shared/rateLimit.ts` every other public/keyed endpoint in this codebase already uses) before doing anything else, mirroring `conversion-postback`'s "rate-limit by the presented key, even if invalid" pattern from G9.

### 3. Endpoints

All under a new `supabase/functions/api-campaigns/index.ts` (one function, path-routed internally on `req.url`'s path suffix and method — matches this codebase's existing convention of one edge function per concern rather than a router framework):

| Method | Path | Behavior |
|---|---|---|
| `GET` | `/v1/campaigns` | List the authenticated advertiser's campaigns (paginated, `?status=` filter). Reads `bookings` scoped to `advertiser_id`. |
| `GET` | `/v1/campaigns/:id` | One campaign's full detail — same fields `AdvDashboard.jsx` already reads, 404 if it doesn't belong to this key's advertiser. |
| `POST` | `/v1/campaigns` | Create a campaign. Body mirrors `CreateCampaign.jsx`'s submission shape (`screen_ids`, `budget`, `start_date`, `end_date`, creative fields, `destination_url`, etc.) — inserted as a `bookings` row with `payment_status: 'pending'`, exactly like a dashboard-created draft before checkout. Does **not** charge; see `POST /v1/campaigns/:id/submit`. |
| `PATCH` | `/v1/campaigns/:id` | Update a pending (not yet submitted/paid) campaign's fields. Rejected with 409 once `payment_status != 'pending'` — same "can't edit after payment" rule the dashboard already enforces on a submitted campaign. |
| `POST` | `/v1/campaigns/:id/submit` | Submits for payment: calls `charge-campaign` internally (server-to-server, service-role — the same function the dashboard's "Pay & Launch" button already calls) using the advertiser's saved default Stripe payment method. Returns the same success/decline shape `charge-campaign` already returns to the dashboard. |
| `POST` | `/v1/campaigns/:id/cancel` | Cancels a scheduled/active campaign — same cancellation path `AdvDashboard.jsx`'s cancel action already uses. |
| `GET` | `/v1/campaigns/:id/delivery` | Read-only delivery summary (impressions, scans, spend to date) — reads the same `campaign_delivery_daily`/`scans` sources `AdvDashboard.jsx` already reads, just via API instead of UI. |

Every write endpoint re-uses the *exact same* insert/update payload shapes and validation `CreateCampaign.jsx` and `charge-campaign` already have — this spec does not re-derive campaign-creation business rules; it's a new entry point into the same rules, which is the point (an API-created campaign is indistinguishable from a dashboard-created one to every other part of the system, same as a house ad or a CSV-imported screen is indistinguishable from a hand-created one).

### 4. Response shape and versioning

JSON, `Content-Type: application/json`, standard HTTP status codes (200/201/400/401/403/404/409/429/500). Path-prefixed `/v1/` from day one even though there's only one version — cheap to do now, expensive to retrofit once a real integration depends on unversioned paths.

## Data flow / state

- Key generation/hashing: client-side (advertiser's own browser), same as G9's postback key.
- All API requests: service-role edge function context (the key *represents* an advertiser but isn't a Supabase auth session, so RLS as an authenticated-user policy doesn't apply here — `api-campaigns` enforces `advertiser_id` scoping in application code after `authenticateApiKey` resolves the caller, the same trust model `conversion-postback` already established for a non-session bearer credential).
- Payment: unchanged — still flows through `charge-campaign`'s existing Stripe off-session logic, just invoked by `POST /v1/campaigns/:id/submit` instead of a dashboard button click.

## Error handling

- Invalid/missing/revoked key: `401`, consistent JSON error body (`{ error: "..." }`) across every endpoint.
- Rate limited: `429`, same shape `conversion-postback` already returns.
- Campaign not found or not owned by this key's advertiser: `404` (not `403` — same "don't confirm existence to an unauthorized caller" reasoning already used elsewhere in this codebase's public/keyed endpoints).
- Attempting to edit a non-pending campaign: `409` with a message naming the actual blocking status.
- `charge-campaign` decline/failure on `/submit`: passed through with the same status/error detail the dashboard's own "Pay & Launch" failure state already surfaces, not swallowed into a generic 500.

## Testing

- `apiKeyAuth.ts`: unit tests for valid key resolves the right advertiser, revoked key rejected, unknown key rejected, `last_used_at` update doesn't block the auth decision.
- `src/lib/apiKey.js`: unit tests mirroring `postbackKey.test.js` (generate/hash, prefix format).
- `api-campaigns/index.ts` per-endpoint tests (extracted pure request-shape validators the same way `create-house-ad`'s `ownership.ts` and `conversion-postback`'s body-parsing are already unit-tested apart from the Deno/network parts): list/get scoping to the caller's own advertiser_id, create builds the same payload shape `CreateCampaign.jsx` would, patch rejects a non-pending campaign with 409, submit forwards to `charge-campaign` and passes through its response.
- `AdvIntegrationsView`'s new "API Keys" section: generation stores a hash not plaintext (mirrors the existing G9 postback-key test), revoke sets `revoked_at`, key list never renders the hash.

Follows this repo's existing per-file `*.test.jsx`/`*.test.ts` convention alongside the files each test covers.

## Open questions for follow-up (not blocking this spec)

- Screen-search/discovery endpoint (`Non-goals`) — revisit once a real integration needs to pick screens programmatically rather than from a known list.
- Webhook/event-push API (`Non-goals`) — revisit once a specific integration requests push instead of poll.
- Delegated-team API scoping matching `account_grants` roles (`Non-goals`) — revisit once an agency-managing-multiple-advertisers use case is real, not hypothetical.
- Whether `scopes` ever needs to vary in practice (read-only keys, campaign-specific keys) — the column exists for this; no product signal yet that it's needed.

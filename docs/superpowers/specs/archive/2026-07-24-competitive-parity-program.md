## 2. Phase 1 — Measurement foundation

**Goal:** three separately-defined, correctly-derived metrics, plus honest trends.

### 2.1 Metric definitions (locked)

Per the IAB DOOH guide, an impression is *one play of a creative on a face, weighted by the audience associated with that play*. AdGrid therefore reports three distinct numbers and labels each:

| Metric | Definition | Source | Label shown |
|---|---|---|---|
| `plays` | One record per creative play on one screen | `ad_plays`, emitted by the player | "verified plays" |
| `impressions` | `Σ plays × audience_multiplier(screen, dow, hour)` | derived | "measured" or "modelled" |
| `attention` | Audience-weighted `avg_attention_score` over the play window | `impression_events` | "attention (CV)" |

`bookings.impressions` becomes a denormalized cache of the derived value, never a direct write target.

### 2.2 New table: `ad_plays`

```sql
CREATE TABLE public.ad_plays (
  id             bigserial PRIMARY KEY,
  campaign_id    uuid NOT NULL REFERENCES bookings(id) ON DELETE CASCADE,
  screen_id      uuid NOT NULL REFERENCES screens(id) ON DELETE CASCADE,
  played_at      timestamptz NOT NULL,
  duration_s     numeric NOT NULL CHECK (duration_s > 0 AND duration_s <= 300),
  completed      boolean NOT NULL DEFAULT true,
  client_play_id text NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (screen_id, client_play_id)
);
CREATE INDEX ad_plays_campaign_played_idx ON ad_plays (campaign_id, played_at DESC);
CREATE INDEX ad_plays_screen_played_idx   ON ad_plays (screen_id, played_at DESC);
```

`client_play_id` is generated by the player (`crypto.randomUUID()`) and makes the ingest idempotent across retries and reconnects. RLS mirrors `impression_events`: service-role insert, operator reads own screens, advertiser reads own campaigns.

### 2.3 New edge function: `ingest-plays`

`POST /functions/v1/ingest-plays`, authenticated by `screen_token` (same pattern as `ingest-impressions`). Accepts a batch (max 200) so the player can buffer offline and flush on reconnect. Upserts on `(screen_id, client_play_id)` with `ignoreDuplicates`. Clamps `duration_s` to ≤300 and rejects `played_at` more than 48h in the past or any time in the future.

`DisplayPlayer` buffers plays in memory (and `localStorage` for offline survival) and flushes every 60s or at 25 buffered plays.

### 2.4 Audience multiplier

```sql
CREATE MATERIALIZED VIEW public.screen_audience_index AS
SELECT
  screen_id,
  EXTRACT(dow  FROM window_start)::int AS dow,
  EXTRACT(hour FROM window_start)::int AS hour,
  avg(people_count / GREATEST(EXTRACT(EPOCH FROM (window_end - window_start)) / 60.0, 1)) AS people_per_min,
  avg(avg_dwell_seconds)   AS avg_dwell_s,
  avg(avg_attention_score) AS avg_attention,
  count(*)                 AS sample_windows
FROM impression_events
WHERE window_end > window_start
GROUP BY 1, 2, 3;
```

Impressions for one play = `people_per_min × (duration_s / 60)`.

Fallback when `sample_windows < 20` for that (screen, dow, hour): modelled from `screens.monthly_traffic_estimate` spread over a venue-type hourly curve (`src/lib/footfallCurves.js`, shared by the Phase 5 forecast). Every delivery row carries `basis text CHECK (basis IN ('measured','modelled'))` so the UI never presents a model as a measurement.

Refreshed by a pg_cron job hourly, alongside the existing crons.

### 2.5 Delivery view

```sql
CREATE VIEW public.campaign_delivery_daily AS ...
-- one row per (campaign_id, screen_id, day) with:
--   plays, completed_plays, impressions, attention_weighted_impressions,
--   scans, billable_scans, basis
```

This single view backs the advertiser dashboard, analytics, Phase 2 reconciliation, Phase 3 reports and benchmarks. No view queries `ad_plays` directly.

### 2.6 Scan quality (S14b)

Add to `scans`: `is_bot boolean default false`, `is_duplicate boolean default false`, `dedup_key text`.

- **Bot:** UA matches `/bot|crawler|spider|preview|facebookexternalhit|slackbot|whatsapp|curl|wget|headless/i`.
- **Duplicate:** same `dedup_key = sha256(campaign_id + screen_id + ip + ua)` seen within 30 minutes.

Rows are always inserted (audit trail intact) and always excluded from reported counts. `billable_scans = scans WHERE NOT is_bot AND NOT is_duplicate`. The advertiser sees "412 scans · 38 filtered as bot/duplicate" — filtering shown, never silent.

### 2.7 Honest trends (G18)

Delete every hardcoded `trend=` prop. Add `src/lib/periodDelta.js`:

```js
export function periodDelta(current, prior) { ... } // null when prior === 0
```

`KPI` renders nothing where the delta is `null` rather than a fake number. Each of the four call sites fetches the prior-period value and passes a real delta.

**Acceptance:** a play on a real screen produces one `ad_plays` row; the advertiser dashboard's impressions come from `campaign_delivery_daily`; a repeated QR scan within 30 min increments total but not billable; no hardcoded trend remains anywhere in `src/`.

## 3. Phase 2 — Trust & delivery

### 3.1 Delivery reconciliation + makegoods (G17)
Nightly cron compares scheduled plays (from schedule × slot share × operating hours) against `ad_plays`, using `display_heartbeats` / `screens.last_seen` to attribute shortfalls to screen downtime. Writes `delivery_reconciliation (campaign_id, screen_id, day, scheduled_plays, delivered_plays, shortfall_pct, credit_amount, reason)`. Shortfall >5% on a paid campaign issues an automatic credit to `profiles.credits` and notifies both sides. Advertiser sees a "Delivery health: 97% of scheduled plays confirmed" card; operator sees downtime attributed to their screen.

### 3.2 Rules & alerts engine (G16)
`automation_rules (id, owner_id, scope, condition_metric, comparator, threshold, window, action, enabled)`. Evaluated by a 15-minute cron over `campaign_delivery_daily`. Actions: notify, pause campaign, adjust daily budget. Ships with three prebuilt advertiser rules and two operator rules enabled by default:
- advertiser: "screen offline >2h during my flight", "pacing <60% of expected at 50% elapsed", "cost-per-scan above target 3 days running"
- operator: "screen offline >30 min", "fill rate <60% for 7 days"

### 3.3 Approval SLA & auto-approve (G7)
`campaign_screens.review_due_at` set on submit (operator's configured SLA, default 24h). Advertiser sees a per-screen approval tracker with expected-by times. Operators define auto-approve policies (`operator_approval_rules`) on top of the existing `content_categories_blocked` — e.g. auto-approve categories X,Y from advertisers with ≥1 completed campaign. On SLA breach, the screen is auto-dropped from the campaign and the advertiser's budget is reallocated or refunded pro-rata; a paid campaign can never be held indefinitely by one silent operator.

## 4. Phase 3 — Reporting & benchmarks

### 4.1 Network benchmarks (G13)
`benchmark_stats` materialized view: p25/p50/p75 of scan rate, cost-per-scan, attention, and CPM grouped by `(venue_category, environment, campaign_category)`. Only groups with ≥5 distinct campaigns *and* ≥3 distinct advertisers are published, so no single advertiser's numbers are inferable. Advertiser sees "your scan rate 0.42% — median 0.31% for Fitness on Retail-Indoor". Operator sees "your CPM floor is 18% below comparable venues".

### 4.2 Reports (G14)
- One-click campaign report: PDF (print-stylesheet route `/report/:campaignId`), branded, includes proof-of-play summary and delivery health.
- CSV export of `campaign_delivery_daily` and the filtered scan log.
- Read-only share link: `campaign_share_tokens (token, campaign_id, expires_at, revoked)` → public route rendering the same report with no auth. Agency can send it to a client.
- Weekly digest email via the existing `notification-cron`.

### 4.3 Reach & frequency (G12)
Estimate unique reach from `screen_audience_index` with an overlap discount for screens within 500m of each other; report `reach`, `avg_frequency = impressions / reach`. Add an optional frequency-cap target in the wizard that trims screen density rather than raising spend.

## 5. Phase 4 — Creative pipeline (parallel track)

### 5.1 Screen creative specs (G2)
Add to `screens`: `resolution_w int`, `resolution_h int`, `orientation text`, `accepted_formats text[] default '{jpg,png,mp4}'`, `max_file_mb int default 25`, `max_duration_s int` (already have `max_ad_duration`). Collected in `ScreenOnboard` and `EditScreenModal`; backfilled from `display_size` where parseable.

Upload validation in Step 3 of the wizard runs against every selected screen and renders a fit matrix: "fits 11 of 14 — 3 need portrait". Missing crops are generated client-side with canvas (smart-crop toward the centre of mass) and stored as per-screen overrides in the existing `campaign_screens.media_url`.

### 5.2 Readability score (G3)
`src/lib/creativeScore.js` — pure, unit-tested: word count, largest-text-height ratio, contrast ratio (WCAG formula), and a blur-test render at a simulated viewing distance derived from venue type and screen size. Score 0–100 with named fixes ("28 words — target under 7 for a 12s play"). Rendered in Step 3 next to the preview, and shown to operators in the approval queue. Advisory, never blocking.

### 5.3 Creative studio (G1)
Template library keyed to aspect ratio; brand kit on `profiles` (logo, 2 colors, font); one-message input produces a compliant layout. AI variant generation is an optional enhancement layered on the same template renderer — the template path must work with no AI call at all.

### 5.4 Variant testing (G15)
`campaign_creatives (id, campaign_id, label, media_url, headline, cta, weight, status)`; `ad_plays.creative_id` and `scans.creative_id` for attribution. Player rotates by weight. Per-variant reporting on scan rate, cost-per-scan and **attention** — the CV signal makes this test better than a click-based one. Optional auto-promote of the winner after a minimum sample.

## 6. Phase 5 — Buying power

### 6.1 Forecast engine (G4)
`src/lib/forecast.js` — pure and unit-tested: `plays/day = operating_hours × 3600 / loop_length × slot_share`, `impressions = plays × multiplier(screen, dow, hour)`, with a confidence band from `sample_windows`. Uses `screen_audience_index` where measured and `footfallCurves.js` where modelled — the same modules Phase 1 introduced. Step 4 shows three budget scenarios (0.5×, 1×, 2×) with projected impressions, plays and cost-per-scan, in the Performance Planner idiom.

### 6.2 Dayparting (G5)
`campaign_dayparts (campaign_id, dow, hour_start, hour_end)`. Hour × day grid in Step 4 with the **measured** footfall heatmap underlaid — a display no competitor can produce. `screens.daypart_multipliers jsonb` lets operators price peak hours above floor; off-peak below. `display-feed` honours the daypart window when selecting creative.

### 6.3 Saved targets, packs, evergreen (G6)
`saved_targets (id, owner_id, name, definition jsonb)` reusable from Step 1. `screen_packs (id, name, curator_id, screen_ids[], description)` for one-click buys. `bookings.is_evergreen boolean` + null `end_date` → daily budget runs until paused; nightly cron charges and tops up.

### 6.4 Audience-index targeting (G22) — the moat
Expose `screen_audience_index` as a targeting dimension: age skew, gender skew, dwell, attention, and hour-of-day index per screen. Advertiser picks "Adults 18–34, high evening index, dwell >8s" and the screen set is selected automatically, each screen showing why it matched. Structurally uncopyable by platforms without cameras on the glass.

### 6.5 Buy-side guardrails (G23)
Frequency cap; max CPM bid; competitive separation (`bookings.category` must not occupy adjacent loop slots — enforced in `display-feed`); share-of-voice guarantee expressed as minimum slot share; advertiser-side venue-type and radius exclusions; operator per-advertiser blocklist.

## 7. Phase 6 — Attribution depth & platform

- **G9 widen:** AdGrid conversion pixel + server postback accepting `adgrid_cid`, inverting the existing `fire-integration` plumbing; promo-code and vanity-URL attribution for non-scanners.
- **G10 holdout:** hold out 20% of eligible screens or postal codes as control; report lift with a confidence interval, following the IAB's matched-market / synthetic-control guidance.
- **G19 OpenOOH:** map `VENUE_TAXONOMY` onto OpenOOH Venue Taxonomy 1.2.1 (3-tier, 11 parents). Cheap now; prerequisite for benchmarks-by-venue and any programmatic connection.
- **G21 API + bulk:** REST campaign API with scoped keys; CSV bulk screen import for operators onboarding 40+ screens.
- **G20 programmatic backfill:** expose unsold loop time via an OpenRTB endpoint or an SSP integration (Vistar / Broadsign Reach / Hivestack), AdGrid demand taking first look. This is the operator-retention argument: unsold loop time stops being worth zero.

## 8. Cross-cutting rules

1. **Never present modelled data as measured.** Every derived number carries a `basis` and the UI labels it.
2. **No fabricated values in UI.** The hardcoded `trend={8}` class of bug is a P0 defect, not polish.
3. **Filtering is shown, not silent.** Bot/duplicate scans, credited shortfalls, and dropped screens are always visible to the affected party.
4. **Pure logic lives in testable modules.** Forecast, scoring, multipliers, and delta math go in `src/lib/*.js` or `supabase/functions/_shared/*.ts` with unit tests — not inline in components.
5. **Tests before implementation**, per the repo's superpowers workflow. Phase 1 Task 1 stands up vitest because the web app currently has no test runner at all.
